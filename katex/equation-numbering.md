# KaTeX draws equation numbers with a CSS counter, not in its output

KaTeX renders TeX to HTML, and it supports the AMS `equation` environment,
so `\begin{equation} ... \end{equation}` produces a numbered display
equation in the browser.

The misleading part is where the number comes from. It is not in the HTML
that KaTeX returns. `renderToString` emits an empty element, and the visible
`(1)` is generated by a CSS rule in `katex.css`. Anything that inspects
KaTeX's output as a string — a test, a grep over a build artifact, a
server-side render — will not find the number, and will conclude the
equation is unnumbered when it is not.

## The number lives in the stylesheet

Rendering an `equation` environment and stripping the tags leaves no number
behind (katex 0.18.7):

```console
$ node -e '
const k = require("katex");
const h = k.renderToString("\\begin{equation}\nx = 1\n\\end{equation}",
                           {displayMode: true});
console.log(h.includes("<span class=\"eqn-num\"></span>"));
console.log(h.replace(/<[^>]+>/g, "").includes("(1)"));
'
true
false
```

The element is empty because `katex.css` fills it in:

```css
.katex .eqn-num::before {
  counter-increment: katexEqnNo;
  content: "(" counter(katexEqnNo) ")";
}

body {
  counter-reset: katexEqnNo mmlEqnNo;
}
```

So the number exists only once a browser applies the stylesheet. Shipping
KaTeX's HTML without `katex.css` silently drops every equation number.

## Numbering is per document, in DOM order

`counter-reset` sits on `body`, and each `.eqn-num::before` increments the
shared `katexEqnNo`. The counter therefore spans the whole document rather
than a section, and the number an equation receives depends on how many
`.eqn-num` elements precede it in the DOM.

The CSS above was read directly; the consequence for pages that mount
content dynamically — a slide deck, a virtualised list — was reasoned from
it, not measured. To settle it, put two `\begin{equation}` blocks on pages
that mount at different times and see which numbers appear.

## There is no `\label`, `\ref` or `\eqref`

A CSS counter cannot be read back by TeX, and KaTeX does not implement the
referencing macros at all. All three are rejected (katex 0.18.7):

```console
$ node -e '
const k = require("katex");
for (const s of ["\\label{eq:a}", "\\ref{eq:a}", "\\eqref{eq:a}"]) {
  try { k.renderToString(s, {throwOnError: true}); console.log(s, "ok"); }
  catch (e) { console.log(s, "->", e.message.split(" at ")[0]); }
}
'
\label{eq:a} -> KaTeX parse error: Undefined control sequence: \label
\ref{eq:a} -> KaTeX parse error: Undefined control sequence: \ref
\eqref{eq:a} -> KaTeX parse error: Undefined control sequence: \eqref
```

KaTeX lists what it does and does not support here:

<https://katex.org/docs/support_table>

## `\tag` writes a static number and leaves the counter alone

`\tag{1}` puts the number in the returned HTML as ordinary text and creates
no `.eqn-num` element, so it neither depends on nor advances `katexEqnNo`:

```console
$ node -e '
const k = require("katex");
const h = k.renderToString("x = 1 \\tag{1}", {displayMode: true});
console.log((h.match(/class="eqn-num"/g) || []).length);
console.log(h.replace(/<[^>]+>/g, "").includes("(1)"));
'
0
true
```

That makes `\tag` the reliable choice when the number has to be known
outside the browser, or when the same equation is restated somewhere else
and both copies must show the same number.

## A macro is the closest thing to a reference

Since there is no `\eqref`, the way to keep a number in one place is a KaTeX
macro, declared through the `macros` option and used on both sides:

```js
const options = { macros: { "\\eqKey": "1" } };
// the equation
k.renderToString("x = 1 \\tag{\\eqKey}", { ...options, displayMode: true });
// the prose reference
k.renderToString("(\\eqKey)", options);
```

Both expand to `(1)`, and changing the macro changes every occurrence. This
is a single source of truth, not automatic numbering: the value is still
written by hand.

Note the failure mode. When the macro is not declared, KaTeX throws
`Undefined control sequence`, and a renderer that catches the error will
usually fall back to printing the raw TeX. Seeing a literal `\tag{\eqKey}`
on the page means the macro never reached KaTeX, not that the syntax is
wrong.
