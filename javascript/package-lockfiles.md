# npm and pnpm lockfiles describe different installation models

`package-lock.json` and `pnpm-lock.yaml` serve the same broad purpose: they
record the dependency resolution selected from the ranges in `package.json`,
so later installs can reproduce it. They are generated by different package
managers and are not interchangeable.

The misleading part is that a lockfile is more than a list of exact package
versions. It also represents enough of its package manager's installation
model to reconstruct `node_modules`. npm and pnpm use different models, so a
project should commit the lockfile belonging to the package manager it uses.

## The three kinds of version are independent

Given:

```json
{
  "version": "1.0.0",
  "packageManager": "pnpm@10.17.1",
  "dependencies": {
    "foo": "^1.2.0"
  }
}
```

these numbers describe separate things:

- `1.0.0` is the project's own version.
- `10.17.1` selects the pnpm CLI used to manage the project.
- `^1.2.0` is the range of acceptable versions of `foo`.
- The lockfile records the particular version of `foo` selected from that
  range, plus its transitive dependency resolution.

There is no numeric correspondence between the pnpm version and dependency
versions. Changing pnpm can change lockfile syntax or resolution behavior,
but it does not require dependencies to have matching version numbers.

## npm records a hoisted dependency tree

npm normally builds a hoisted `node_modules`. If `foo` depends on `bar`, npm
may place both at the project root when their constraints permit it:

```text
node_modules/
├── foo/
└── bar/
```

This reduces duplication, but it can make `bar` resolvable by application
code even when only `foo` declares it. Code that relies on this accidental
access has a phantom dependency: it may break when the dependency tree is
rearranged.

`package-lock.json` describes the exact tree npm generated. npm documents
that it is generated when npm changes `node_modules` or `package.json`, and
that subsequent installs use it to reproduce the same tree:

<https://docs.npmjs.com/files/package-lock.json/>

## pnpm separates resolution from shared storage

pnpm stores package files in a content-addressable store shared across
projects. It hard-links files from that store into a project's virtual store
under `node_modules/.pnpm`, then uses symbolic links to expose the dependency
graph.

Conceptually:

```text
global content-addressable store
        │ hard links
        ▼
node_modules/.pnpm/<package instance>/node_modules/<package>
        │ symbolic links
        ▼
node_modules/<direct dependency>
```

Only declared direct dependencies are normally linked at the project root.
A dependency can still reach its own declared dependencies through links in
its package instance, while application code cannot normally import an
undeclared transitive dependency by accident.

pnpm documents the shared store, links, and stricter root visibility here:

<https://pnpm.io/symlinked-node-modules-structure>

`pnpm-lock.yaml` records the resolution pnpm needs for this model. pnpm also
uses one lockfile for all projects in a workspace by default. Its install
documentation confirms that `--frozen-lockfile` refuses to generate or
update the lockfile and fails when it is absent or out of sync:

<https://pnpm.io/cli/install>

## Use one package manager's lockfile

For an npm project, commit `package-lock.json` and use `npm install` or
`npm ci`. For a pnpm project, commit `pnpm-lock.yaml` and use `pnpm install`.
Do not maintain both as parallel sources of truth: each can resolve and
change independently.

When migrating an existing npm project, `pnpm import` can create a
`pnpm-lock.yaml` from `package-lock.json`:

<https://pnpm.io/cli/import>

After migration, use pnpm consistently and remove the obsolete npm lockfile.
